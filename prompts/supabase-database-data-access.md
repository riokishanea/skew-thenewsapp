# Supabase database and data access

## Goal

Add the secure Supabase persistence foundation for Skew News: a versioned SQL schema for the six canonical pipeline tables, strongly typed server-only Supabase clients, and small query modules for sources, articles, analyses, logs, and scheduler records. This establishes the data contract required by later scraping, AI analysis, scheduling, and UI work without implementing those workflows or changing the existing static pages.

## Decisions and assumptions

- This is a foundation-only change. Do not replace preview article arrays, add route handlers, scrape sources, call AI, create schedules remotely, seed invented sources, or enable pgvector yet.
- Use a `supabase/schema.sql` source-of-truth SQL file because this repository does not currently have a Supabase CLI project, declarative schema setup, or migrations directory. The user will execute the SQL in Supabase Dashboard → SQL Editor before database-backed features are tested.
- Install the pinned `@supabase/supabase-js` dependency and retain the lockfile.
- Add a required unique article `slug`, generated by future ingestion code, because the existing detail route is `/news/[slug]`. Slugs are a public application identifier—not a replacement for URL deduplication.
- Use UUID primary keys and UTC `timestamptz` timestamps. Preserve both `original_url` and optional `canonical_url`; each is uniquely constrained when present, and ingestion will perform both dedupe checks.
- The initial schema deliberately excludes the `embedding vector(1536)` column and all vector/RPC/index work; that is a later pgvector scope.
- The application uses Clerk, not Supabase Auth. Data access is therefore server-only through the Supabase service-role client. No browser Supabase client is needed in this slice.
- All public-schema tables enable RLS. Revoke `anon` and `authenticated` privileges from the six tables and create no browser-facing policies: the Next.js server service role is the only access path. The service role remains server-only and bypasses RLS.
- Store Oxylabs schedule and job identifiers as `text`, never numeric, to preserve their 64-bit precision. Store scheduler payload/metadata and log context as JSONB.
- Use small, explicit query functions. Avoid joined-table filter expressions such as `.eq('foreignTable.column', value)`; select relation data then filter in TypeScript only where later needed.

## Implementation requirements

1. Install `@supabase/supabase-js` at an exact version and commit its lockfile changes.
2. Add all canonical environment-variable placeholders to `.env.example`:
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY`
   Keep the existing Clerk variables and do not add `CRON_SECRET`.
3. Create `supabase/schema.sql` containing idempotent initial-schema SQL for:
   - `sources`: name, `listing_url`, optional parser strategy/logo URL, active flag, timestamps, and a unique homepage URL.
   - `articles`: source foreign key, original/canonical URLs, unique slug, title, required image URL/published date/raw article text, scrape/analyze timestamps, and query indexes for source/date, analyzed state, and slug.
   - `article_analyses`: one-to-one article foreign key; summary, sentiment score/label, AI-estimated framing distribution and label, derived bias score, confidence, framing notes, loaded terms, disclaimer, model, timestamps; checks for valid ranges and a distribution totaling 100.
   - `logs`: pipeline/run metadata, severity, message, optional source/article references, structured JSON context, and timestamp.
   - `oxylabs_schedules`: source foreign key, text schedule identifier, enabled state, scheduler cadence/state/payload metadata, and timestamps.
   - `oxylabs_schedule_runs`: schedule foreign key, text job/run identifiers, status/result status, result metadata, started/finished timestamps, and uniqueness appropriate to one recorded job per schedule.
4. Make database constraints reflect the contract instead of relying only on TypeScript: nonempty URLs/titles/text, valid sentiment and framing labels, bounded numeric scores, and percentage-total validation. Do not add categories, regions, user data, or speculative tables.
5. Enable RLS for every new public table; explicitly revoke `anon` and `authenticated` table privileges. Do not create permissive policies and do not expose the service-role key.
6. Define a complete `Database` type in `lib/supabase/types.ts` that matches the SQL tables, row/insert/update shapes, JSON fields, nullable timestamps, and relation-compatible IDs. Keep application-specific result types adjacent to the relevant query module when they are not raw table shapes.
7. Create one browser-safe public client factory using only `NEXT_PUBLIC_SUPABASE_*` values, and a separate `server-only` service-role factory that validates required server environment values before constructing the client. Do not import the service client from client components.
8. Add query modules with explicit return types and descriptive thrown errors for at least:
   - `getActiveSources()` and `getSourceById()`.
   - `getArticleBySlug()` with its source and analysis relation, returning `null` when absent.
   - `getPublishedArticles()` for analyzed home-feed records, newest first, with a bounded configurable limit.
   - `findExistingArticleUrls(urls)` that chunks `.in()` checks to no more than 15 URLs.
   - `insertArticle()` as append-only persistence, with no update/delete helper.
   - `getPendingAnalysisArticles()` based on the absence of an `article_analyses` relation (not `analyzed_at` alone), suitable for batched later analysis.
   - `insertArticleAnalysisAndMarkAnalyzed()` that only marks `articles.analyzed_at` after the analysis insert succeeds; document that a later transaction/RPC can strengthen this atomicity if needed.
   - `insertLog()`, plus schedule/run read and upsert-record helpers needed by later pipeline routes.
9. Keep data access in `lib/supabase/**`; pages and route handlers will consume these functions later. Do not make UI components perform persistence, scraping, analysis, or scheduler work.

## Security requirements

- Never read, print, commit, or return `.env.local` values.
- Never expose `SUPABASE_SERVICE_ROLE_KEY` through `NEXT_PUBLIC_*`, route output, client code, or error messages.
- RLS is enabled across every public table, with public roles having no table access in this server-only architecture.
- Foreign keys use suitable deletion behavior that protects append-only article history; do not add a cascade that silently deletes articles when a source is removed.
- Do not use Supabase Auth or `auth.uid()` policies; Clerk remains the authentication provider.

## Acceptance criteria

- `supabase/schema.sql` is sufficient to create the six canonical tables safely in a new Supabase project and contains no pgvector column.
- The schema has table-level constraints, indexes, foreign keys, RLS, and least-privilege grants/revocations appropriate for server-only access.
- TypeScript types accurately represent all schema fields.
- The public client cannot access the service role, and the service client is guarded by `server-only` plus runtime environment validation.
- Query functions support the exact later needs for active-source selection, append-only article storage/dedupe, homepage/details reads, pending analysis, logging, and scheduler record persistence.
- Existing static home, detail, and Clerk flows remain visually and behaviorally unchanged.

## Manual test steps after implementation

1. Copy the Supabase placeholders from `.env.example` into `.env.local` and fill them with the project values. Do not put `CRON_SECRET` in `.env.local`.
2. In Supabase Dashboard → SQL Editor, run `supabase/schema.sql` once against the intended development project.
3. In SQL Editor, verify the schema and RLS with:

   ```sql
   select tablename, rowsecurity
   from pg_tables
   where schemaname = 'public'
     and tablename in ('sources', 'articles', 'article_analyses', 'logs', 'oxylabs_schedules', 'oxylabs_schedule_runs')
   order by tablename;
   ```

   Confirm six rows are returned and every `rowsecurity` value is `true`.
4. Start the app with `npm run dev`; confirm the existing home page and a signed-in `/news/<slug>` preview route still render without Supabase credentials appearing in browser developer tools.
5. When a later server route or server component is wired to `getActiveSources()`, insert a test source in SQL Editor and confirm it is returned only through that server-side path. Do not call the service-role client from browser JavaScript.
